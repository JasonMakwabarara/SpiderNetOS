# Awareness list

Priestley's Awareness A: surface things before they fester into incidents. Add an entry the moment you notice something, even mid-unrelated-task — don't silently fix it (raises blast radius of your current change) and don't silently ignore it (loses the finding). Move an entry to "Resolved" with the commit/PR once addressed.

## Open

- **The rest of the cockpit's agent views are still tested against hand-written fixtures the backend never produced.** The approval path now has a generated contract fixture (next paragraph). `tests/fixtures/agent_run.json` does not. It uses artifact statuses `pending_approval` (the backend writes `submitted`), kinds `message_template` (the backend writes `draft_email` and `draft_sequence`), and `content` as an object (the backend returns text). So `AgentRunDetail`'s tests pass against a run the server cannot return; its `artifactPill()` styles a status that never occurs. The generated-fixture pattern (`ApprovalApiContractTest` → `cockpit/tests/fixtures/contract/`) is the fix, applied one endpoint at a time.
- **Five cockpit stores show test fixtures when their API fails.** `runs`, `board`, `brain`, `map` and `skills` (plus `AtlasLaunchPanel`) import files from `tests/fixtures/` into production code and, on a failed request, display them under "Showing sample data". A person can read and act on fictional runs, maps or skills that look like their own. The approvals store does not do this, so a decision is never made on sample data. This is a product decision: either keep sample data for demos behind an explicit demo mode, or show the failure.

**Resolved in commit 4c** (the cockpit's approval editor and the artifacts API disagreed on shape, so editing an agent draft from the Approvals page could not work). The page read the draft from `context.artifact`, which the backend never wrote, and saved `content` as an object where the API takes text; its test ran on a fixture of exactly that fictional shape. The page now renders `context.payload`, the payload the approval binds. It saves each step as `Subject: …\n\nbody` text with the version it started from, and decides on the version captured with what is on screen. `runs.patchArtifact()` serialises the text form in one place; `AgentRunDetail` had the same object bug and now sends artifacts under review to their approval. The approvals store had also sent the approver's comment as `comment`, which the API ignores; it now sends `reason`. The page is tested against a fixture the backend generates from a real run.
- **`AggregateUsageJob` writes `usage.aggregate.persisted` straight into `event_log`, around `EventStore`, and the write probably never succeeds.** `emitPersistEvent()` (`backend/app/Jobs/AggregateUsageJob.php:198`) inserts with no `version` (declared `integer`, NOT NULL, no default, in `2024_01_01_000001_create_event_log_table.php:19`) and a fixed `sequence_num => 0` on a unique column, and it swallows the exception with a warning. So the event should fail on every run. **Inferred from the migration, not run.** Even if it succeeded, it would carry no HMAC, no `previous_hash` link and no sequence lock. Its test (`tests/Unit/Jobs/AggregateUsageJobTest.php:45`) only checks that the source contains the event name. The job is on `main`, independent of PR #100, and is tracked as its own task: reproduce, find the consumer, route it through `EventStore` or remove it.

**Resolved in commit 5b** (`EventStore::append()` read an aggregate's version before taking the sequence lock, so two concurrent appends to one aggregate both computed *n+1* and the unique index failed one with a 500). The sequence lock is now taken first and the version is read under it, so concurrent appends to one aggregate take consecutive versions in lock order. A stale `expected_version` is now `EventVersionConflict`, a `RuntimeException` naming the expected and found versions, raised under the lock rather than surfacing as the index's database error. The unique index stays as the backstop. `tests/Feature/Events/EventAppendRaceTest` pins it with two separate Postgres processes queued behind a held sequence lock, and reproduced the original failure before the fix. When the loser conflicts, the business row it wrote in the same transaction rolls back with it. What it does not settle: whether a caller that catches the conflict should retry. That still depends on what already committed, so nothing retries automatically.
- **Parked agent runs can stay parked forever after their tool call is approved. This blocks any workflow that relies on approved agent resumption.** `AgentRunResumer` records the decision on the run and dispatches `ResumeAgentRunJob` with `afterCommit()`. Three pieces sit outside the database's transaction:
  - The queue is Redis in every checked-in config.
  - The job is `ShouldBeUnique`, so its lock is written to the cache store (Redis) at dispatch time, *before* commit.
  - The push itself happens after commit.

  Confirmed by a read-only review with an adversarial second pass (inferred from code and vendor source; not executed), the resume can be lost in four ways:
  - A process that dies between commit and push leaves the decision recorded and nothing queued.
  - A failed push after commit.
  - A rollback after the resumer's savepoint had committed leaks the unique lock. A retry inside its 300 s window then dispatches nothing, silently.
  - A resume job released by `TenantRunSlot` with `tries = 1` fails before it claims the run. The review judged this the most likely.

  Each loss is permanent. `FailStaleAgentRunsJob` only touches claimed or running runs. `retry()` refuses `waiting_approval`. No sweeper looks for a decided-but-parked run. The chain and expiry paths have the same windows, and no action record at all.

  What changed in the 5a corrections: `agent_tool_call` is no longer declared `transactional`. As `external`, a crash or a failed push ends `uncertain` rather than `done`. The misreport of a post-commit failure as `pending` is fixed too. Neither change delivers the resume.

  The fix the review recommends is a level-triggered sweep over run rows whose decision is recorded but that were never resumed, plus an `approval_id` guard in `ResumeAgentRunJob::handle()`. Add a process-death test *after* the action commits and *before* the dispatch. The existing crash test kills the process earlier.
- **Chain and expiry approvals run their hooks inside the decision's transaction, with no action record.** A hook failure rolls the decision back, so these paths never commit an unexecuted decision. The price is twofold:
  - An external effect cannot be rolled back. A chain whose last step approves an `outreach_reply` sends mail (SMTP, and an HTTP call to Affonso, with no idempotency key) while holding the approval row and the global event-sequence lock. A later failure in that transaction, or a retry, can send it twice.
  - A registered hook whose class is missing is still skipped silently on these paths.

  Confirmed reachability at this commit: the payment hook is DB-only and nothing creates `payment` approvals. `bill` and `expense_report` fire only on chains and expiry. Step expiry voids a bill terminally, with a null reason. An `outreach_reply` chain is exercised in tests. A deterministic hook failure on the expiry path blocks every later overdue step (head-of-line).

  Any external-effect handler on these paths needs the `ApprovalActions` policy, or the path stays disabled for it. Moving a path onto `ApprovalActions` changes its failure semantics from "rolls back" to "decided, action owed", which is a decision to take deliberately.
- **An approval type with no hook at all still records its action as done.** A registered hook whose class is missing now fails (`hook_missing`). But a resource type that appears in neither `approvals.resource_hooks` nor the legacy switch is treated as needing nothing, and its action is marked done. The review of 2026-09-28 asks for an explicit no-action declaration per type, so that "requires no follow-up" is a decision someone made rather than an inference from absence. That needs an inventory of the resource types approvals are actually created with.
- **`uncertain` and `failed` actions have no operational owner yet.** They are visible in three places: the `approval_actions` table (`status`, a machine-readable `reason`, `last_error`, `attempts`), the log, and the exit code of `approvals:recover-actions`, which is non-zero while any exist. The Approvals page tells the decider at the moment it happens: "waiting to be retried", "needs checking" or "needs attention". After that, nothing shows it to anyone, and nothing lets a person reconcile one.

  The minimum is an admin command or view with:
  - action and approval identity;
  - the bound version and the destination;
  - the attempt history and last error;
  - a provider request id where one exists;
  - a controlled way to record the reconciled outcome.

  An expired external claim is already turned into `uncertain`, never re-sent.
- **The recovery schedule only exists where a scheduler runs.** `approvals:recover-actions` is scheduled every five minutes in `routes/console.php`. Three things decide whether it runs:
  - **Docker compose (observed):** `backend/docker-entrypoint.sh` ignores the container command and always ends in `exec php artisan serve`. So the compose `horizon` and `scheduler` services would run a web server, not workers or the scheduler.
  - **Production:** runs on systemd (fpm plus `spidernetos-horizon.service`). No scheduler unit or cron entry for `schedule:run` is recorded.
  - **Unknown:** whether any scheduled job (this one, `ExpireApprovalStepsJob`, `FailStaleAgentRunsJob`) runs in production. Establish it on the box before relying on recovery. That is why the API says "waiting to be retried", not "will be retried".
- **Lock-order cycles around the global event-sequence lock (review of 2026-09-28; confirmed, mostly low likelihood).** The 5b reorder added no new lock edge, and the reviewer's exact artifact-then-sequence scenario is not reachable. Other pairs do take the same locks in opposite orders, and Postgres will abort one side with a deadlock:
  - **D1 (medium):** a single-stage rejection's action against a grant or chain finalisation for the same tenant and skill, on `tenant_skills` against `event_sequence`.
  - **D2:** `brain_files` and `message_templates` against the sequence, when two sequence grants in one tenant overlap.
  - **D3 and D4:** `approvals` against `agent_artifacts`, in chain rejection or expiry against the artifact endpoints, and in a grant and a rejection of one role-based step.
  - **D5:** `approval_steps` against `approvals`, in expiry against resolve and delegate.
  - **D6:** `bills` against the sequence.
  - **D7:** `partner_prospects` against the sequence, outside approvals.

  Worse than the deadlocks themselves (medium, partly confirmed): catch-all handlers *inside* transactions swallow the failure without a savepoint. These are the notification helpers in `ApprovalEngine`, `BillService` and `ExpenseService`, and the projectors that run inside `EventStore::append`. On Postgres a swallowed SQL error, a deadlock included, leaves the transaction aborted, and everything after it fails. `BestEffort` already shows the fix: a savepoint, and rethrow on deadlock.
- **Re-running the database seeder wedges the event store (inferred, not run).** `DatabaseSeeder` ends with `updateOrInsert(['id' => 1], ['next_num' => 100])` and no `max()` guard. On a second `db:seed` (`make seed`, or the entrypoint when its user count reads 0 because `psql` failed), the counter goes back to a number already used. Every later append then fails on the unique `sequence_num` until someone repairs it by hand. The fix: drop the reset, since the store advances the counter itself, or set `next_num = greatest(next_num, max(sequence_num) + 1)`.

  The review also answered the first-append question. The migration creates the table and its row together, and nothing deletes the row, so the absent-row branch in `getNextSequenceNum()` is not reachable in normal operation. If the row were missing on a database that already has events, numbering would restart at 1 and wedge in the same way. Unsettled: the Python intelligence worker writes `event_sequence` with an unguarded insert of its own.

**Partly resolved in commit 5a, corrected after review** (an approval could commit and its downstream effect never happen, and nothing noticed). What is true now:
- **Recording and running:** the single-stage decision writes an `approval_actions` record in its own transaction and runs it after the commit. `approvals:recover-actions` retries what is `pending`, where a scheduler runs (see above).
- **Delivery declarations:** each resource type declares how its record runs (`approvals.action_delivery`), and anything undeclared is external.
  - **Transactional:** `agent_artifact` and `business_plan`, each checked against its hook. These run inside one transaction with their record: locked, re-checked, marked done. A replay is a no-op, and a failure rolls the hook back and stays `pending`. A failure *after* the commit, in something the hook deferred, is `uncertain`, not `pending`.
  - **External:** everything else, `agent_tool_call` included. These are claimed and committed before they run. One that fails, or claims and never reports back, becomes `uncertain` and is never re-run blind.
- **What ends `failed`:** a registered hook whose class is missing, an integrity failure, or attempts running out. Every outcome other than `done` carries a machine-readable `reason`.
- **Evidence:** a real process killed after commit on Postgres, with two recoveries racing for its record, applied once, the approved version. The in-process policy matrix on every driver. And separate-session proofs that a failed best-effort write leaves the required writes committed, while a failed required write leaves only the decision and the owed action.

## Resolved this cycle (Lead-to-Sale Funnel bundle)

- **`ApprovalController::approve()`/`reject()` referenced non-existent columns** (`resolved_by`, `resolved_at`) instead of the real schema's `approver_id`/`responded_at` — every call to `POST /api/approvals/{id}/approve|reject` (the cockpit's actual Approvals page action) threw a 500. This is the platform's core human-in-the-loop mechanism; fixed as part of wiring the funnel's script-approval step through it. `backend/app/Http/Controllers/ApprovalController.php`.
- **`ApprovalEngine::resumeBlockedExecution()` updated the wrong table** (`dag_nodes`, a read-only projection) instead of `execution_dag_nodes` (what `DagExecutionService` actually reads). Fixed; `ApprovalEngine` is used by `VoiceSafetyGuard` today and will matter more once other flows create DAG-linked approvals.
- **Dynamic agent slugs weren't pack-namespaced**, contrary to `docs/feature-packs/SPEC.md` isolation rule #3 — `FeaturePackInstaller`/`SpidernetPackInstall` slugged agents as bare `Str::slug($agentId)`, so two packs both defining a `crm` or `growth` agent would collide on the same tenant. Fixed to `{pack_id}_{agent_id}` (both slugified).
- **`ste_transitions.chain` / `ste_event_mapping.chain` were `varchar(32)`**, too narrow for pack-namespaced chain names (`pack.real-estate-crm.lead_lifecycle` is 35 chars) — seeding any pack's STE mappings would have failed on insert. Widened to `varchar(64)`.
- **`phpunit.xml` set `CACHE_DRIVER=array`, but `config/cache.php` reads `CACHE_STORE`** (Laravel 11 rename) — the override was a silent no-op, meaning tests using the cache facade were hitting a real Redis connection attempt instead of the intended in-memory array store. Fixed to `CACHE_STORE`.
- **`FunnelSetupService::funnelArchitectAgentId()` looked up the wrong slug format** (`sales-crm_funnel_architect`, hyphen preserved) — the real installer produces `sales_crm_funnel_architect` (`Str::slug()` turns the hyphen into an underscore). Caught by an integration test that used the real installer instead of a hand-matched fixture.
- **`OperatingController::orgChart()` read `manifest['roles']`** instead of `manifest['spec']['roles']` (roles live under `spec:` like everything else in a pack manifest, per `real-estate-crm`'s convention). Fixed.
- **`OperatingController::scoreboard()` read `manifest['spec']['targets']`** instead of `manifest['spec']['provides']['targets']` (targets are nested under `provides:`, matching `docs/feature-packs/SPEC.md`). Fixed.
- **`SpidernetPackInstall` (CLI) duplicated `FeaturePackInstaller`'s install logic** end to end and never went through entitlement gating. Refactored to delegate to the shared service so `--grant` and future gating changes apply uniformly to both the CLI and HTTP paths.
