# Awareness list

Priestley's Awareness A: surface things before they fester into incidents. Add an entry the moment you notice something, even mid-unrelated-task — don't silently fix it (raises blast radius of your current change) and don't silently ignore it (loses the finding). Move an entry to "Resolved" with the commit/PR once addressed.

## Open

- **Removing the `notes/zetkai/**` manifest pattern would silently downgrade personal notes to `internal`.** Stage 5 of the brain plan says to delete the ZetKai integration including that brain pattern. `packages/brain/manifest.yaml:480` declares `data_class: personal` for it; `BrainManifest::dataClass()` (`:230-233`) returns `DEFAULT_DATA_CLASS = 'internal'` (`:22`) whenever `fileSpec()` matches no pattern. So any existing `brain_files` row under `notes/zetkai/` becomes unmatched and is reclassified **personal — internal**, which is exactly the class `BrainVisibility` and the Stage 0A retrieval filter key on. The sync job is scheduled nightly (`backend/routes/console.php:59`, `dailyAt('02:30')`) behind three flags that default off, so whether any rows exist is an environment question, not a source one — check before removing anything. A removal needs either a data migration reclassifying those rows or a retained pattern; it is not a cleanup. Note also that `ZetKaiSyncService.php:148-167` is the only working tombstone-on-delete pattern in the repo, and Stage 5 separately wants tombstones for `brain_links`.
- **`identities.yaml` declares 44 skills; 35 have no card, and 33 of those sit under identities marked `status: existing`.** Only 9 skill directories exist under `packages/skills/`. Both Stage 7 targets are among the phantoms and both are marked existing: `diagram` and `screenshot-to-code` (`identities.yaml:236-242`). `linkedin-campaign-runner` is given as Richard's only skill (`:106`) with no directory, while the card that does exist, `linkedin-outreach-specialist`, declares `runs_on: growth`. `SkillRegistry::isPlannedSkill()` treats a roster slug with no card as planned rather than an error, which is a deliberate and reasonable choice — but it means the roster file asserts existence for 33 things that do not exist, and nothing reconciles the two directions. The registry pattern this repo applies to suppressions, deferrals and test suites is not applied to the roster itself.
- **Two semgrep findings are unaccounted for, and they are a CI blocker on `feature/brain-workspaces`.** `security/check_findings.py` fails on any finding that `security/exceptions.yaml` does not cover. Identified rather than described: `intelligence/services/business_launch/docgen.py:104` `python.jinja2.security.audit.autoescape-disabled-false.incorrect-autoescape-disabled`, and `inference/tts_providers.py:32` `python.lang.security.use-defused-xml.use-defused-xml`. Each needs either a fix or a classified exceptions entry with a reason, an owner and a review date — never a suppression to get the tick. The first is a template-injection surface if any of that document content is attacker-influenced; the second is XML parsing without `defusedxml`. Both are judgement calls about untrusted input and neither should be waved through as "internal only" without establishing that. Run `35703331926`.
- **`phpunit.xml`'s `CiFast` suite re-registers files already in `Unit`, producing 21 PHPUnit runner warnings on any local run that loads all suites.** `CiFast` selects a subset by repeating directories that sit inside `./tests/Unit` (`Ste`, `Payments`, `Billing`, `Mfa`, `Outreach`, and `Skills`, added 2026-09-21), so PHPUnit 11 reports *"Cannot add file X to test suite CiFast as it was already added to test suite Unit"* once per file. Harmless to correctness — `--testsuite=CiFast` and `--testsuite=Unit` each run cleanly, which is what CI does — but every local run ends *"OK, but there were issues!"*, which trains people to ignore the warning block where a real warning would appear. The fix is to select the fast lane by group or attribute rather than by a duplicate suite; not done inline because it changes how CI selects tests. `backend/phpunit.xml:14-30`.
- **Larastan fails branch-wide on `feature/brain-workspaces`, and the baseline predates the branch.** Stage 0B fixed static analysis and regenerated `phpstan-baseline.neon` on `chore/ci-green`, which merged to `main`; the 29 commits of branch code were never checked against it. CI reports **144 diagnostics** on `a3f37fb` (tested merge `0a3ef81`). The **sets were compared**, not just the totals: every `##[error]` message from the `a3f37fb` run and the `6279b29` run, with digits normalised so line numbers may shift, sorted and diffed — identical, 144 on each side. So no diagnostic appeared and none disappeared across those two revisions. The limitation is worth naming: the `##[error]` lines carry the message only, not the file or the rule id, so two findings with the same message in different files would not be told apart. A file-plus-rule comparison needs the raw PHPStan output rather than the annotations. By message shape: 34 `will always evaluate to true`, 1 to false, 11 `call has no effect`, 33 unnecessary nullsafe or redundant syntax, 2 missing classes (`BrainExport`/`BrainImport`), and ~63 typing and contract errors. **These are not one problem and must not be fixed as one.** An `always true` can mean an earlier check already guarantees the condition, or that a PHPDoc promises more than runtime inputs do — so each is read at its source, and **a defensive check at an external-input boundary is not deleted to satisfy the analyser**. `call has no effect` is removable once its intent is checked; `unnecessary nullsafe` needs the non-null guarantee confirmed first; the missing classes are a stale-reference or autoload question; the typing and contract errors are caller/callee disagreements and are the real work. Roughly 32% may be redundant-code cleanup, but the risk is per category, not per count. A full run before the nine Stage 1 fixes reported ~154; a full run before the nine Stage 1 fixes reported ~154 — `FounderBriefService` 16, `SkillCatalogue` 12, `SkillLoop` 8, `BoardController` 8, `SkillPromptBuilder` 7, `BusinessMapService` 7, `AtlasDiscoveryService` 7, `AgentRunner` 7, and a long tail. The `backend — lint + static analysis` job has therefore been red for the whole feature and nobody saw it while GitHub Actions was billing-blocked. Nine of them were introduced by the Stage 1 commits and are fixed; `app/Services/Skills/Eval` is clean. The remainder is a merge blocker for PR #100 and is its own change, not Stage 1's — missing `BrainExport`/`BrainImport`, `Carbon\Carbon` vs `Illuminate\Support\Carbon` parameter mismatches, a `facts` key absent from a declared return shape, Eloquent typing, and `env()` outside config, before any redundant-condition cleanup. Reproduce with `php vendor/bin/phpstan.phar analyse --memory-limit=1G` from `backend/`.
- **`StripeAdapter` posts to a non-existent Stripe endpoint.** `createPaymentIntent()` and `verifyPayment()` both call `https://api.stripe.com/v1/payment_intentions` — the real endpoint is `payment_intents` (no trailing "io"). - **`scripts/validate_feature_pack.py` checks the wrong path for pack signatures**, so the documented "fail closed on placeholder signatures" behavior never actually runs. - **`entryPathForPack()` / `entryPath()` is duplicated three times** with the same `match` expression: `FeaturePackController.php`, `FeaturePackInstaller.php`, `PackGrowthService.php`. Adding a new pack's entry route means remembering to update all three. Worth consolidating into one shared source (e.g. a `entry_path` field on the manifest, or a single lookup service) next time a pack is added.
- **`NodeActionRunner::runNotify()` / `runReminder()` are stubs** for every pack except sales-crm, which bypasses them entirely via dedicated `send_email`/`send_whatsapp` agent tools (`intelligence/tools/registry.py`) instead of the generic DAG `notify` node. real-estate-crm and financial-services flows that use `notify`/`reminder` nodes still don't actually send anything.
- **Cross-pack STE event-name collisions are possible.** `sales-crm.lead_lifecycle` and `real-estate-crm.lead_lifecycle` both map generic event names (`lead.form.submitted`, `deal.won`, etc.) rather than pack-namespaced ones — `real-estate-crm` set this precedent, `sales-crm` followed it for consistency. If a tenant ever installs both packs, one `lead.form.submitted` event advances both chains' Markov counts simultaneously. Low practical risk (the verticals don't usually co-install) but worth a namespacing pass if that ever becomes real.

## Resolved this cycle (Lead-to-Sale Funnel bundle)

- **`ApprovalController::approve()`/`reject()` referenced non-existent columns** (`resolved_by`, `resolved_at`) instead of the real schema's `approver_id`/`responded_at` — every call to `POST /api/approvals/{id}/approve|reject` (the cockpit's actual Approvals page action) threw a 500. This is the platform's core human-in-the-loop mechanism; fixed as part of wiring the funnel's script-approval step through it. `backend/app/Http/Controllers/ApprovalController.php`.
- **`ApprovalEngine::resumeBlockedExecution()` updated the wrong table** (`dag_nodes`, a read-only projection) instead of `execution_dag_nodes` (what `DagExecutionService` actually reads). Fixed; `ApprovalEngine` is used by `VoiceSafetyGuard` today and will matter more once other flows create DAG-linked approvals.
- **Dynamic agent slugs weren't pack-namespaced**, contrary to `docs/feature-packs/SPEC.md` isolation rule #3 — `FeaturePackInstaller`/`SpidernetPackInstall` slugged agents as bare `Str::slug($agentId)`, so two packs both defining a `crm` or `growth` agent would collide on the same tenant. Fixed to `{pack_id}_{agent_id}` (both slugified).
- **`ste_transitions.chain` / `ste_event_mapping.chain` were `varchar(32)`**, too narrow for pack-namespaced chain names (`pack.real-estate-crm.lead_lifecycle` is 35 chars) — seeding any pack's STE mappings would have failed on insert. Widened to `varchar(64)`.
- **`phpunit.xml` set `CACHE_DRIVER=array`, but `config/cache.php` reads `CACHE_STORE`** (Laravel 11 rename) — the override was a silent no-op, meaning tests using the cache facade were hitting a real Redis connection attempt instead of the intended in-memory array store. Fixed to `CACHE_STORE`.
- **`FunnelSetupService::funnelArchitectAgentId()` looked up the wrong slug format** (`sales-crm_funnel_architect`, hyphen preserved) — the real installer produces `sales_crm_funnel_architect` (`Str::slug()` turns the hyphen into an underscore). Caught by an integration test that used the real installer instead of a hand-matched fixture.
- **`OperatingController::orgChart()` read `manifest['roles']`** instead of `manifest['spec']['roles']` (roles live under `spec:` like everything else in a pack manifest, per `real-estate-crm`'s convention). Fixed.
- **`OperatingController::scoreboard()` read `manifest['spec']['targets']`** instead of `manifest['spec']['provides']['targets']` (targets are nested under `provides:`, matching `docs/feature-packs/SPEC.md`). Fixed.
- **`SpidernetPackInstall` (CLI) duplicated `FeaturePackInstaller`'s install logic** end to end and never went through entitlement gating. Refactored to delegate to the shared service so `--grant` and future gating changes apply uniformly to both the CLI and HTTP paths.
