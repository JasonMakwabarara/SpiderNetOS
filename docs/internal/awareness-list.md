# Awareness list

Priestley's Awareness A: surface things before they fester into incidents. Add an entry the moment you notice something, even mid-unrelated-task — don't silently fix it (raises blast radius of your current change) and don't silently ignore it (loses the finding). Move an entry to "Resolved" with the commit/PR once addressed.

## Open

- **Larastan fails branch-wide on `feature/brain-workspaces`, and the baseline predates the branch.** Stage 0B fixed static analysis and regenerated `phpstan-baseline.neon` on `chore/ci-green`, which merged to `main`; the 29 commits of branch code were never checked against it. A full run reports ~154 unbaselined errors — `FounderBriefService` 16, `SkillCatalogue` 12, `SkillLoop` 8, `BoardController` 8, `SkillPromptBuilder` 7, `BusinessMapService` 7, `AtlasDiscoveryService` 7, `AgentRunner` 7, and a long tail. The `backend — lint + static analysis` job has therefore been red for the whole feature and nobody saw it while GitHub Actions was billing-blocked. Nine of them were introduced by the Stage 1 commits and are fixed; `app/Services/Skills/Eval` is clean. The remaining ~145 are a merge blocker for PR #100 and are their own task, not Stage 1's. Reproduce with `php vendor/bin/phpstan.phar analyse --memory-limit=1G` from `backend/`.
- **`StripeAdapter` posts to a non-existent Stripe endpoint.** `createPaymentIntent()` and `verifyPayment()` both call `https://api.stripe.com/v1/payment_intentions` — the real endpoint is `payment_intents` (no trailing "io"). Anything relying on Stripe payment intents is currently broken. Not fixed as part of the Dodo Payments work since `DodoPaymentsAdapter` doesn't share code with it — flagged so nobody copies the typo forward. `backend/app/Services/Integrations/StripeAdapter.php:30,171`.
- **`scripts/validate_feature_pack.py` checks the wrong path for pack signatures**, so the documented "fail closed on placeholder signatures" behavior never actually runs. It reads `spec.provides.signatures`, but every real pack (including the new `sales-crm`) puts `signatures:` at `spec.signatures` (sibling of `provides`), per `docs/feature-packs/SPEC.md`. Net effect: placeholder signatures currently pass validation silently. `scripts/validate_feature_pack.py:79`.
- **`entryPathForPack()` / `entryPath()` is duplicated three times** with the same `match` expression: `FeaturePackController.php`, `FeaturePackInstaller.php`, `PackGrowthService.php`. Adding a new pack's entry route means remembering to update all three. Worth consolidating into one shared source (e.g. a `entry_path` field on the manifest, or a single lookup service) next time a pack is added.
- **`NodeActionRunner::runNotify()` / `runReminder()` are stubs** for every pack except sales-crm, which bypasses them entirely via dedicated `send_email`/`send_whatsapp` agent tools (`intelligence/tools/registry.py`) instead of the generic DAG `notify` node. real-estate-crm and financial-services flows that use `notify`/`reminder` nodes still don't actually send anything.
- **Cross-pack STE event-name collisions are possible.** `sales-crm.lead_lifecycle` and `real-estate-crm.lead_lifecycle` both map generic event names (`lead.form.submitted`, `deal.won`, etc.) rather than pack-namespaced ones — `real-estate-crm` set this precedent, `sales-crm` followed it for consistency. If a tenant ever installs both packs, one `lead.form.submitted` event advances both chains' Markov counts simultaneously. Low practical risk (the verticals don't usually co-install) but worth a namespacing pass if that ever becomes real.
- **`vendor/` was missing `symfony/yaml`** despite it being a direct `composer.json` dependency (`^7.0`) — every other symfony package was present. This silently broke `FeaturePackController::loadCatalogueEntries()`, `FeaturePackInstaller::install()`, and `SpidernetPackInstall` (all call `Yaml::parseFile()`), i.e. the entire feature-pack catalogue/install subsystem, in this checkout. Fixed locally via `composer install --ignore-platform-reqs` (the full non-ignored install fails on this native-Windows PHP because `laravel/horizon` needs `ext-pcntl`/`ext-posix`, which don't exist on Windows — that's expected, the project's real dev path is the Docker stack). **Action: confirm `composer.lock` is fully installed in CI/deploy images**, since this gap would not have been visible from `composer.json` alone.
- **CAC:LTV has no real computation.** `GET /api/operating/scoreboard` returns `null` for `cac_ltv_ratio` — there's no ad-spend/CAC tracking yet. Needs either a financial-services pack integration or a manual-entry field on the alignment profile.
- **WhatsApp per-tenant number provisioning is manual.** `messaging_numbers` rows have to be created directly (no automated "buy a Twilio number for this tenant" flow yet), unlike the existing voice number provisioning path.
- **Autonomous-mode WhatsApp auto-replies aren't content-safety-gated.** The inbound webhook (`WhatsAppController::inbound`) logs and dispatches for a reply but the actual send-vs-draft decision by `automation_level` isn't enforced by a `VoiceSafetyGuard`-equivalent filter yet — only documented as the intended behavior in a code comment. Needs a hard gate before enabling autonomous sends in production.
- **`tests/Feature/**` (including the pre-existing `FeaturePackApiTest` and the new `tests/Feature/Sales/*`) cannot run against the sqlite `:memory:` connection configured in `phpunit.xml`**, because `database/migrations/2024_01_01_000006_create_memory_table.php` creates a pgvector `vector` column with no sqlite equivalent (`RuntimeException: This database driver does not support the vector type`). This is pre-existing — confirmed by running the untouched `FeaturePackApiTest` before adding anything. The new Lead-to-Sale Funnel Feature tests were verified by manually running the underlying migrations/logic against sqlite outside `RefreshDatabase` (skipping the vector-dependent migration) during development; they still need a real run against the project's Postgres+pgvector stack to go green in CI.

## Resolved this cycle (Lead-to-Sale Funnel bundle)

- **`ApprovalController::approve()`/`reject()` referenced non-existent columns** (`resolved_by`, `resolved_at`) instead of the real schema's `approver_id`/`responded_at` — every call to `POST /api/approvals/{id}/approve|reject` (the cockpit's actual Approvals page action) threw a 500. This is the platform's core human-in-the-loop mechanism; fixed as part of wiring the funnel's script-approval step through it. `backend/app/Http/Controllers/ApprovalController.php`.
- **`ApprovalEngine::resumeBlockedExecution()` updated the wrong table** (`dag_nodes`, a read-only projection) instead of `execution_dag_nodes` (what `DagExecutionService` actually reads). Fixed; `ApprovalEngine` is used by `VoiceSafetyGuard` today and will matter more once other flows create DAG-linked approvals.
- **Dynamic agent slugs weren't pack-namespaced**, contrary to `docs/feature-packs/SPEC.md` isolation rule #3 — `FeaturePackInstaller`/`SpidernetPackInstall` slugged agents as bare `Str::slug($agentId)`, so two packs both defining a `crm` or `growth` agent would collide on the same tenant. Fixed to `{pack_id}_{agent_id}` (both slugified).
- **`ste_transitions.chain` / `ste_event_mapping.chain` were `varchar(32)`**, too narrow for pack-namespaced chain names (`pack.real-estate-crm.lead_lifecycle` is 35 chars) — seeding any pack's STE mappings would have failed on insert. Widened to `varchar(64)`.
- **`phpunit.xml` set `CACHE_DRIVER=array`, but `config/cache.php` reads `CACHE_STORE`** (Laravel 11 rename) — the override was a silent no-op, meaning tests using the cache facade were hitting a real Redis connection attempt instead of the intended in-memory array store. Fixed to `CACHE_STORE`.
- **`FunnelSetupService::funnelArchitectAgentId()` looked up the wrong slug format** (`sales-crm_funnel_architect`, hyphen preserved) — the real installer produces `sales_crm_funnel_architect` (`Str::slug()` turns the hyphen into an underscore). Caught by an integration test that used the real installer instead of a hand-matched fixture.
- **`OperatingController::orgChart()` read `manifest['roles']`** instead of `manifest['spec']['roles']` (roles live under `spec:` like everything else in a pack manifest, per `real-estate-crm`'s convention). Fixed.
- **`OperatingController::scoreboard()` read `manifest['spec']['targets']`** instead of `manifest['spec']['provides']['targets']` (targets are nested under `provides:`, matching `docs/feature-packs/SPEC.md`). Fixed.
- **`SpidernetPackInstall` (CLI) duplicated `FeaturePackInstaller`'s install logic** end to end and never went through entitlement gating. Refactored to delegate to the shared service so `--grant` and future gating changes apply uniformly to both the CLI and HTTP paths.
