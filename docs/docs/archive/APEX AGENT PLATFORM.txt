1. Executive Summary and Target Operating Model
Apex should be built as a four-plane agent platform with one dominant application operating on 
top of it first: Hannah Flow. Hannah Flow is the first production product because it is closest to 
your current Boa Flow work and has the clearest revenue and operational payoff. Atlas is the 
internal engineering plane built second, Apex Intelligence is the supervisory plane built third, and 
SpiderNet OS is the multi-tenant commercialization layer built fourth.
The key design principle is simple: the user experiences one click, but the system executes a 
managed graph of specialist agents, bounded tools, explicit approvals, queue-isolated workloads, 
and event-backed replay. This approach matches OpenAI’s practical guidance that manager-pattern 
orchestration with specialist delegates is usually safer and more maintainable than one monolithic 
autonomous agent [R1]. It also aligns with Laravel’s first-party support for queues, Horizon, 
notifications, scheduler-driven workflows, and Livewire-powered administrative interfaces [R2]
[R3][R4][R5].
The three existing Hetzner servers are sufficient for a credible version-one platform if they are 
assigned clean boundaries. The largest node becomes the Control plus Intelligence plane. The 
existing Boa AI node becomes the Action plane. The Atlas node becomes the Engineering plane. A

3. Service Boundaries and Laravel vs Python Ownership
This platform will only remain governable if service boundaries are respected. The most important 
operational rule is this: Laravel owns workflow truth and business truth. Python owns tool use, 
compute-heavy execution, and inference. Python services may perform work, but Laravel persists 
the official state transitions, approvals, and audit history.
3.1 Laravel ownership
• Identity, SSO, role and permission model, workspace and tenant boundaries
• Templates, versions, flow definitions, publish rules, approval rules
• FlowExecutionService and durable execution records
• Agent registry, instruction profiles, guardrail profiles, approval policies, secret scopes
• Super-admin cockpit APIs, dashboard views, queue health summaries, replay console metadata
• Notification routing, approval inbox, event persistence, KPI materialization and summaries
3.2 Python ownership
• Playwright/browser automation, crawling and extraction, document conversion, screenshoting, 
media assembly
• Atlas repository analysis, code generation helpers, static review, test writing, patch bundling
• Inference gateway and local model serving
• Heavy connectors and worker runtimes that would bloat or destabilize the PHP application
3.3 Contract between layers
1. Laravel creates an execution intent and persists the parent execution, stage, and job records.
2. Laravel dispatches a signed internal job payload onto a queue or internal service endpoint.
3. Python executes the requested work under explicit runtime limits and tool permissions.
4. Python returns structured outputs, metrics, and artifact references.
5. Laravel persists canonical status, approval state, replay metadata, and notifications.
This contract prevents hidden state drift and makes event replay, approvals, and incident analysis 
practical.

The cockpit assistant is a dedicated operations agent that consumes the event stream, queue and 
node health, approval backlog, and performance metrics, then translates that into useful

8.2 Authorization model
Use Laravel gates and policies consistently. Every agent, flow, approval, replay request, and 
assistant command should be authorization-aware. Super admins can do everything. Operators can 
manage jobs and replays but should not silently rewrite policy. Approvers can action approvals but 
not redesign flows. Auditors can inspect everything but cannot mutate records.
Gate::define('manage-cockpit', fn (User $user) => $user->hasRole('super_admin') || $user->hasRole('operator'));
Gate::define('approve-high-impact-actions', fn (User $user) => $user->hasRole('super_admin') || $user
>hasRole('approver'));
Gate::define('view-audit-and-replay', fn (User $user) => $user->hasAnyRole(['super_admin', 'operator', 
'auditor']));

10. Agent Registry CRUD System
The agent registry is the workforce management system for the platform. It is where the super 
admin or delegated operators define what agents exist, what they are allowed to do, which queues 
they may service, which models they prefer, what approval policies they must honor, and how they 
are measured.
10.1 Create flow
1. Open Agent Registry and choose Create Agent.
2. Set identity fields: name, slug, product scope, role, runtime type.
3. Set provider and default model, or mark as Laravel-managed if model-free.
4. Bind allowed queue families and allowed job types.
5. Select instruction profile, guardrail profile, approval policy, and secret scope.
6. Set runtime guardrails such as max runtime, token cap, artifact size cap.
7. Save agent and optionally create one or more tasks immediately.
10.2 Update flow
All changes should be version-audited. Update operations should write an audit event describing 
who changed what and whether the change affected runtime permissions, models, tools, or 
approval requirements.
10.3 Archive / deactivate flow
Agents should rarely be hard-deleted. Use deactivate or archive semantics. Any in-flight execution 
that depends on the agent should either continue with the existing snapshot or fail safely according 
to policy.

12. Cockpit Assistant Backend Logic and Notification System
The cockpit assistant should be implemented as an operations-oriented agent, not as a generic chat 
endpoint. Its job is to convert telemetry into action. It consumes event and metric streams, 
produces concise summaries, raises notifications, and supports a bounded set of commands. It 
should inherit the super admin context only when the authenticated user has the necessary 
permission.
12.1 Responsibilities
• Generate morning brief and periodic summary cards
• Alert on approvals waiting beyond threshold
• Alert on anomaly or KPI deterioration
• Answer natural-language operational questions using the event store and materialized metrics
• Suggest next-best actions with direct deep links into the cockpit
• Dispatch bounded commands such as running a health check or opening a replay view

15. Security, Approvals, Replay, Testing, and Acceptance Criteria
15.1 Non-negotiable security rules
• Python services never become the source of truth for execution state.
• No direct DB writes from external worker services except through explicitly sanctioned internal 
APIs or carefully scoped service accounts.
• Production publishing remains approval-gated until trust thresholds are proven.
• Atlas cannot deploy directly to production by default.
• All high-impact actions write a durable audit and event record.
• Third-party skills, packages, or agent tools are treated as untrusted until reviewed and pinned.
• NemoClaw/OpenShell patterns may inform staged experimentation, but production trust 
remains with your own scoped-permission and approval system while NemoClaw is alpha [R10]
[R11].
15.2 Event replay
Every execution should be replayable. The replay console should let the super admin inspect the 
original request, stage and job transitions, tool invocations, outputs, approvals, and failure points. 
Replay does not necessarily mean re-execute; it means reconstruct the history faithfully and 
optionally fork a new run from a chosen safe point.
15.3 Feature-test acceptance criteria
1. A super admin can create an agent, attach tasks, and see the agent in the registry.
Apex Agent Platform Implementation Document
2. A super admin can build a Hannah template in the builder, save it, validate it, and publish a 
version.
3. A Hannah execution persists execution, stage, job, artifact, and event records correctly.
4. An approval node pauses execution and resumes only after explicit approval.
5. A cockpit notification is created when a high-severity anomaly or approval event occurs.
6. The cockpit assistant can answer a bounded question such as "What needs my attention?" using
