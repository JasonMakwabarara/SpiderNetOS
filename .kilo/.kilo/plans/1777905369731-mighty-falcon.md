# Implementation Plan: Feature Pack Registry API + CI Backend-Test-Full

## Overview

Two deliverables:

1. **`GET /api/feature-packs`** — Auth + tenant-scoped REST API listing installed feature packs, backed by database records created during `spidernet:pack-install`.
2. **`backend-test-full` CI job** — GitHub Actions job running the full PHPUnit suite against Postgres (pgvector) + Redis, covering `tests/Feature/` including `PostgresOnly/AgentDelegationTenantIsolationTest.php`.

---

## Part 1: Feature Pack Registry API

### Step 1: Database Migration — `feature_packs` table

**File:** `backend/database/migrations/2026_05_05_000001_create_feature_packs_table.php`

Create a table tracking installed packs per tenant:

| Column | Type | Notes |
|--------|------|-------|
| `id` | UUID | Primary key |
| `tenant_id` | UUID | FK → tenants, indexed |
| `pack_id` | string | e.g. `real-estate-crm` |
| `version` | string | SemVer from manifest |
| `vertical` | string | Industry classification |
| `display_name` | string | Human-readable name |
| `description` | text | Nullable |
| `manifest` | JSON | Full parsed pack.yaml |
| `status` | string | `installed`, `active`, `disabled` |
| `installed_at` | timestamp | When pack was staged |
| `timestamps` | standard | created_at, updated_at |

- Composite unique: `(tenant_id, pack_id)` — one install per tenant per pack.
- Indexes: `tenant_id`, `status`, `vertical`.

### Step 2: Model — `FeaturePack`

**File:** `backend/app/Models/FeaturePack.php`

- Extends `Model` with `HasUuids`.
- `fillable`: all columns above except timestamps.
- `casts`: `manifest` → `array`.
- Relationships:
  - `belongsTo(Tenant::class)` — inverse of `Tenant::hasMany(FeaturePack::class)`.
- Helper methods:
  - `getAgentsAttribute()` — returns `manifest['spec']['provides']['dynamic_agents']`.
  - `getFlowsAttribute()` — returns `manifest['spec']['provides']['flows']`.
  - `isActive()` — returns `status === 'active'`.

### Step 3: Update `Tenant` Model

**File:** `backend/app/Models/Tenant.php`

Add relationship:
```php
public function featurePacks(): HasMany
{
    return $this->hasMany(FeaturePack::class);
}
```

### Step 4: Update `SpidernetPackInstall` Command

**File:** `backend/app/Console/Commands/SpidernetPackInstall.php`

After copying pack to `storage/app/feature-packs/{id}`:
1. Parse the YAML manifest (use Symfony YAML component already in Laravel).
2. Upsert a `FeaturePack` record for the current tenant (resolved via `--tenant` option or first active tenant in single-tenant mode).
3. Add `--tenant` option to specify which tenant to install for.

The command should:
- Accept `--tenant=<id>` (optional, defaults to first active tenant if single).
- Parse `pack.yaml` using `Symfony\Component\Yaml\Yaml`.
- Create/update the `FeaturePack` row with parsed manifest data.

### Step 5: Controller — `FeaturePackController`

**File:** `backend/app/Http/Controllers/FeaturePackController.php`

Methods:

- **`index(Request $request)`** — `GET /api/feature-packs`
  - Scope: `$request->user()->tenant->featurePacks()` (tenant-isolated).
  - Optional query params: `?vertical=...`, `?status=...`.
  - Response: `{ "data": [...] }` with pack metadata (id, pack_id, version, vertical, display_name, description, status, agents, flows, installed_at).

- **`show(Request $request, string $id)`** — `GET /api/feature-packs/{id}`
  - Scope: tenant + pack_id.
  - Returns full manifest + install details.
  - 404 if not found for this tenant.

### Step 6: Routes

**File:** `backend/routes/api.php`

Add inside the existing protected middleware group (`auth:sanctum`, `tenant`, `onboarding.required`, `cost.limit`, `throttle:api`):

```php
Route::get('/feature-packs', [FeaturePackController::class, 'index']);
Route::get('/feature-packs/{id}', [FeaturePackController::class, 'show']);
```

## Part 2: CI Backend-Test-Full Job

### Step 1: Add `backend-test-full` job to CI workflow

**File:** `.github/workflows/ci.yml`

Append a new job:

```yaml
backend-test-full:
  name: backend — full test suite (Postgres + Redis)
  runs-on: ubuntu-latest
  services:
    postgres:
      image: pgvector/pgvector:pg15
      env:
        POSTGRES_USER: spidernet
        POSTGRES_PASSWORD: spidernet
        POSTGRES_DB: spidernet_test
      ports:
        - 5432:5432
      options: >-
        --health-cmd pg_isready
        --health-interval 10s
        --health-timeout 5s
        --health-retries 5
    redis:
      image: redis:7-alpine
      ports:
        - 6379:6379
      options: >-
        --health-cmd "redis-cli ping"
        --health-interval 10s
        --health-timeout 5s
        --health-retries 5
  defaults:
    run:
      working-directory: backend
  steps:
    - uses: actions/checkout@v4
    - uses: shivammathur/setup-php@v2
      with:
        php-version: '8.2'
        extensions: mbstring, xml, pdo_pgsql, bcmath
        coverage: none
    - uses: actions/cache@v4
      with:
        path: backend/vendor
        key: composer-${{ runner.os }}-${{ hashFiles('backend/composer.lock') }}
    - run: composer install --prefer-dist --no-progress --no-interaction
    - name: Wait for Postgres
      run: |
        until pg_isready -h localhost -U spidernet -d spidernet_test; do
          sleep 1
        done
    - name: Migrate
      run: php artisan migrate --force
    - name: Run full PHPUnit suite
      run: ./vendor/bin/phpunit -c phpunit.github-full.xml
```

### Step 2: Verify CiFast suite doesn't overlap with Feature tests

The current `CiFast` testsuite only runs `tests/Unit/Ste` — no overlap with `tests/Feature/`. This is correct. The `backend-test-full` job will run `Unit` + `Feature` suites (including `PostgresOnly/`).

### Step 3: Make CiFast overlap note (hygiene)

The ROADMAP mentions: "CiFast overlaps `tests/Unit/Ste`" — this is actually the *only* thing CiFast runs, so there's no duplication. The `phpunit.xml` default `Feature` testsuite covers `tests/Feature` which never runs locally without `--testsuite=Feature`. This is by design; no action needed.

## Risks & Mitigations

- **YAML parsing in PHP**: Laravel ships with `symfony/yaml` — already available. No new dependency needed.
- **SQLite vs Postgres migration**: The `feature_packs` table uses only standard types (UUID, JSON, string) — fully SQLite-compatible for CiFast tests.
- **Tenant resolution in CLI**: The `--tenant` option is optional; default to first active tenant for simplicity in single-tenant setups.
- **Redis in CiFast**: The `FeatureFlag` service uses Redis, but tests already handle this via `FeatureFlag::set()`/`forget()` in testing mode. New tests will follow the same pattern.
